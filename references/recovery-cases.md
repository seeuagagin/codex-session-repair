# 历史案例与分流

以下来自 2026-11-14 对历史聊天的定向审阅，描述当时版本和证据范围。历史建议、组件自检、原会话实测及用户验收分别判断；再次使用前核对当前安装版本与接口。历史里的命令和用户批准不授权重放操作。

## 历史不可见，数据仍在

**历史证据：** 2026-06 的列表故障记录显示，本地 active 记录仍在，不同 provider/source 过滤导致近期列表只显示少量聊天；更新替换 app.asar 后复发。2026-11 的 ChatGPT.app 案例修改近期列表的 provider 过滤后，用户明确回复“已经恢复了”。后续技能维护另有离线测试，不能把它当成同次重开应用验证。

**处理：**

1. 确认是本机 Codex 历史还是 ChatGPT 云端 Projects；核对账号、host、归档、项目视图。用正式列表及已知 UUID 读取证明内容是否存在。
2. 证实 provider/source 过滤时，复用已安装的 `$codex-app-show-all-threads`，先读其当前 SKILL.md 和 dry-run 结果。该技能负责应用版本适配、完整性、备份和回退；不在本技能复制补丁。
3. 应用包补丁需对应授权，会使原厂签名失效；重启后实际检查目标聊天可见且可读。列表修复不能证明跨 provider 续聊已恢复，还须按主技能验证。
4. 更新后复发，核对当前包版本、哈希及补丁入口是否实际生效；不要安装旧版已修改 ASAR，也不要自动创建重打补丁的后台任务。

**未采纳的旧推测：** 另一个历史聊天曾猜测 CodexManager 或 disable_response_storage 导致不可见，没有修复后实测。仅凭备份目录存在或配置键出现不能判定因果；不将改开关、恢复旧库写成默认修复。

## 压缩模型与普通对话模型不同

**历史证据：** 2026-09 的“修复会话压缩模型错误”最初把 unsupported model 归因于会话保存模型；后续查到普通会话使用另一模型，而网关 compact 实际使用旧默认模型。还发现 Compose 未将环境变量传入容器，仅改 .env 不会生效。最终记录证明配置加载、健康检查与哈希一致，明确写了“尚未执行真实压缩请求”；没有原会话恢复或用户验收证据。

**处理：**

- 关联失败 turn、请求 ID、请求路径、客户端 model、网关映射和实际 upstream model。没有报错的聊天可能没有触发同类压缩，不能用其显示模型推断压缩模型。
- 区分客户端配置、网关全局 compact 配置、账号映射及普通模型权限。历史 Sub2API 使用过 GATEWAY_OPENAI_COMPACT_MODEL；当前支持项与优先级须查对应版本源码/文档，不硬编码旧模型名，不臆造 compact_model 等 TOML 键。
- 修复应落在有证据的层。网关部署交给对应项目及 `$newapi-fix` / `$sub2api-safe-upgrade` 的适用流程，保持原会话历史；本地会话修复授权不自动覆盖服务器变更。
- 验证配置实际进入运行进程，再验证原会话真实 compact 成功及后续续聊。健康检查 200 只证明服务健康；普通模型列表隐藏某模型也不证明普通请求已被禁止。

## 命令宿主入口缺失

**历史证据：** 2026-07 CLI 0.144.0 案例记录：codex 主入口可用，同版本 arm64 宿主二进制存在，但本地 bin 缺 codex-code-mode-host 链接。补回指向 standalone/current/bin 的链接，限时 --version 返回 0。可读历史只有助手自检记录，未见原会话执行命令后的确认；安装中断/清理误删属于可能原因，未证实。

**处理：** 核对实际安装方式、主 CLI 的真实路径/版本、宿主的来源、架构、可执行性和 PATH。只有同版本可信二进制已存在且入口确实缺失时，才在授权范围恢复对应入口；不要覆盖现有未知文件或链接，不跨版本拼装宿主，也不要从未知来源下载替代。当前版本未使用该组件时，按当前安装修复方式处理。

**验证：** 先限时启动自检，再在原会话执行无敏感信息、无远程副作用的本地命令。修好工具执行入口无需删聊天或改审批设置；仅 --version 成功不能宣告原会话恢复。

## 加密工具结果与正文占位符

**历史证据：** 2026-11 有旧多代理业务聊天连续两个 failed turn，错误为 `Encrypted function output content could not be decrypted or decoded.`；另一测试聊天能创建子代理并回传，但首次任务与追加任务正文均成 `Encrypted content omitted`。前者有真实失败 turn，后者有端到端失败记录；历史里的桥接修复建议尚未实施验证。

**处理：**

- 将 provider 对 reasoning item 的 invalid_encrypted_content、function output 解码失败、消息正文占位分别定位，不能仅凭 encrypted 字样套用同一回退边界。
- 对正文占位，用不同无敏感标记追踪调用参数、授权解码、消息构造及接收正文；创建成功和回传成功仍可能伴随任务丢失。若获准测试，分别覆盖 spawn、follow-up、send-message，要求接收方精确复述标记。
- `encrypted: true` 的 schema 标注本身不证明故障。不要删除标签或将日志脱敏文本用作真实任务；无法解析应明确失败，不能默默派发占位符。
- 历史提到的 BPS“省略加密内容”开关是有内容损失的桥接兼容候选，未证实能修复该案例。仅当当前桥接实现有受支持选项、用户接受具体丢失范围且快照已核验时再评估；需保留消息顺序、工具调用与结果对应关系，不能用通用 JSONL 删除替代。占位文本不恢复被省略的任务或工具结果，应补充必要明文后验证。
- 确定需回退历史时，再读 [保留历史并修复](history-repair.md)，以准确 turn 和授权范围为边界；不是所有 function output 错误都需要删除历史。

## 续接业务与会话数据修复分开

“恢复会话并继续工作”的历史聊天后续实际执行了业务开发和交接，没有证明会话存储故障。检索时区分任务续接与数据修复：前者读取交接、分支、脏改动、活动执行者与暂停状态；不要因为标题有“恢复”就改会话数据、恢复备份或重启业务。

## 按备份用途决定保留范围

历史可见性补丁验收后只清理临时候选，保留一份原始应用文件回退副本；加密会话修复则在用户明确要求后删除专用聊天快照及临时文件。二者没有统一“保留一份”或“全部删除”策略。

沿修复回执识别备份用途和依赖。ChatGPT.app 的 app.asar 与 Info.plist 属于同一回退组，需要一起保留或按获批范围处理；只留其中一个可能无法完整回退。应用更新后重新核对备份对应版本。精确清理仍沿 [验收后清理](backup-cleanup.md)，不将保留策略扩展到其他修复、全局备份或第三方管理器目录。
